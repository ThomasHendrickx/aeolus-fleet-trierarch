# 0039 Sessions in containers, by default, each trierarch's choice

- A trierarch runs its sessions on the host or each in its own container. Its configuration picks: left out, containers, once the default holds; `{ "kind": "host" }`, the host; `{ "kind": "container" }`, containers, refusing to start on what would not hold. It is no crew setting and no label, and placement never reads it (0027): a crew request does not care how its session runs. It is each trierarch's, not the computer's: two trierarchs on one computer each pick their own. The trierarch states its runtime in its report's details as a fact (0028), and why it runs on the host when its configuration leaves the runtime out.
- The default holds when the trierarch runs on Linux, a session image of its version exists for its architecture, the runtime answers rootless with pasta, and every harness its configuration offers is proven in a container for that release's image. Each condition that fails is a reason, all stated at once; until all hold its sessions run on the host. macOS keeps the host until Colima, an Apple-chip image and Mac logins are proven (#473).
- A crewed ship keeps the runtime its ship folder was made for, a worktree on the host or a clone in a container, through restarts and new settings versions; it moves only when its folder is made fresh. A runtime that breaks while containers ran fails starts within the restart budget and gives new requests back; the host is used only once a trierarch start reads the default again.
- The session runtime is the trierarch's `SessionRuntime` port (list, start, stop, send, interrupt, events), with two adapters: host and container, each with one hold per session on the host (trierarch.md "Session runtime"). The container adapter's hold runs one container per ship, named after its ship id, attached (`run -i`), so sending a line, interrupting a turn and reading the events are the hold's, as on the host, and the container lives as long as its hold. A harness that runs a process per turn runs each turn with `exec` into it. The hold reads the container's exit (its status, past its memory cap) before it removes it, and a start removes a leftover of its name. Crewing, the launch window, wakes, restarts, give-backs and release stay as they are.
- Runtimes: rootless only, Podman on Linux and Colima on macOS, behind one adapter speaking the docker-style commands they share, the binary named in the configuration (`podman` when left out). Never a user in the docker group, never the runtime's socket inside a container. The trierarch starts a dead session again itself; no restart policy of the runtime. Hard memory, CPU and process caps per session, from the configuration, with defaults when it names none. A read-only root, so everything a session writes lands in its ship's folder. A container's hold lives outside the service's control group, so an upgrade ends no session.
- A container sees its workspace, its own home (the files of its own harness, the aeolus-fleet plugin, its ship's identity file without a crew token), a folder holding its ship's socket to the trierarch (0026), its short-lived access and its repository's key. Nothing else of the host. The trierarch prepares that home before every launch (identity, trust, onboarding), as it prepares the host's today.
- The workspace is a per-ship clone, not a worktree: `git clone --reference <the configured repository> --dissociate`, so it holds its own objects and no gc of the host's repository can break it. Release and a clear request remove the clone, named by its ship and repository (0032).
- Logins: the host's harness keeps its login and renews it. The trierarch never renews a login itself and never copies a refresh token, and a container gets only an access that ends with its session or within the hour: through the model proxy, the session's own proxy token, which the proxy swaps for the host's current access (a subscription login, the long-lived `claude setup-token` token included, or an API key), only towards that harness's vendor; or, where a harness cannot be pointed at the proxy, an access file holding the host login's current access token alone, mounted read-only and written again before it ends. A container reaches the proxy through pasta forwarding only the proxy's port, so no other host service is reachable (PR 287). A login that cannot be renewed is reported and argo told with the step on the host; new crews for that harness are given back. No session has Remote Control: `config check` refuses `--remote-control` on every runtime. The fleet is reached through the aeolus-fleet plugin over the trierarch's socket, never a claude.ai connector; the container needs no route to the fleet. Narrowing its egress is a later setting of the trierarch.
- Keys per repository, in the trierarch's configuration: a ship crewed on a repository gets that repository's key, and no other.
- The image is published by `release.yml` with the release's version (0011), for `linux/amd64` and `linux/arm64`, with every harness proven in it at a pinned version and its aeolus-fleet plugin. A trierarch uses its own version's image, and a running container keeps its image until its next start; an upgrade pulls the new version's image before it restarts the service, and is refused when it cannot. The configuration may name another image per repository, built on the published one.

Why: every session on a computer runs as one user, so one rogue or breached session on the host can read every ship's crew token, worktree, model login and keys, kill the trierarch or another session, and send as any ship on the computer around the network rules (0034). A container holds a session to its own ship, so it is the default and the host the exception. A harness is moved into a container only once proven there, so the default never breaks a ship. A refresh token rotates or reaches the person's whole account: one copy on the host, used by the harness that made it, keeps the person signed in and every ship working, and a leaked access ends soon. A worktree points into the main checkout's `.git`, which holds every other ship's worktree data and the hooks, so mounting it would let a session plant a hook that runs on the host; a clone holds nothing of the host. Several trierarchs may run on one computer, each with its own work, so the runtime is the trierarch's. A published image brings a new trierarch up fast.

Rejected: a crew setting or label (a request does not care how its session runs); a setting per computer (a computer may run several trierarchs); moving a crewed ship between a worktree and a clone (its work could be lost); a user in the docker group (root-equivalent); OrbStack, Apple's `container` and Docker Desktop on macOS (memory leaks outside the VM's limit, too many open files, licences); the worktree with the main `.git` mounted writable (a way out of the container); `.git` mounted read-only (the session could not commit or branch); a clone with `--reference` and no `--dissociate` (a gc of the host's repository breaks it); the host's full login, or any refresh token, in a container (every session holds the login); a long-lived token in a container where the proxy can stand in; keys per ship name (a ship may be crewed on any computer) or as a crew option (more moving parts); building from `devcontainer.json` at crew time (slow, and it can fail mid-launch; a later option); a VM per tenant (only when compute is sold).
