# 0039 Sessions in containers, a machine's choice

- A trierarch runs its sessions on the host or each in its own container. The machine's configuration picks one session runtime for all its sessions, host by default. It is no crew setting and no label, and placement never reads it (0027): a crew request does not care how its session runs. The trierarch states its runtime in its report's details as a fact (0028).
- The session runtime is the trierarch's `SessionRuntime` port (list, start, stop, send, interrupt, events), with two adapters: host (one hold per session, trierarch.md "Session runtime") and container. The container adapter runs one container per ship, named after its ship id, with tmux inside, so sending a line, interrupting a turn and reading the events, which are the screen's lines, are an exec into it. Crewing, the launch window, wakes, restarts, give-backs and release stay as they are.
- Runtimes: rootless only, Podman on Linux and Colima on macOS, behind one adapter speaking the docker-style commands they share, the binary named in the configuration. Never a user in the docker group, never the runtime's socket inside a container. The trierarch starts a dead container again itself, as it restarts a session; no restart policy of the runtime. Hard memory and CPU caps per session, from the configuration. A container started from the service lives outside its control group, so an upgrade ends no session.
- A container sees its workspace, its own home (the harness's config folder, the aeolus plugin, its ship's identity file without a crew token), a folder holding its ship's socket to the trierarch (0026), the model login and its repository's key. Nothing else of the host. The trierarch prepares that home before every launch (identity, trust, onboarding), as it prepares the host's today.
- The workspace is a per-ship clone, not a worktree: `git clone --reference <the configured repository> --dissociate`, so it holds its own objects and no gc of the host's repository can break it. Release and a clear request remove the clone, named by its ship and repository (0032).
- The model login: one long-lived token per machine (`claude setup-token`), handed to each container. No session has Remote Control: `config check` refuses `--remote-control` on every runtime. Container mode offers Claude Code only, until Codex is proven in a container. The fleet is reached through the aeolus plugin over the trierarch's socket, never a claude.ai connector; the container needs no route to the fleet. Narrowing its egress is a later machine setting.
- Keys per repository, in the machine's configuration: a ship crewed on a repository gets that repository's key, and no other.
- The image is published by `release.yml` with the release's version (0011). A trierarch uses its own version's image, and a running container keeps its image until its next start. The configuration may name another image per repository, built on the published one.

Why: every session on a machine runs as one user, so one rogue or breached session can read every ship's crew token, worktree, model login and keys, kill the trierarch or another session, and send as any ship on the machine around the network rules (0034). A container holds a session to its own ship. A worktree points into the main checkout's `.git`, which holds every other ship's worktree data and the hooks, so mounting it would let a session plant a hook that runs on the host; a clone holds nothing of the host. The trierarch knows the hardware it runs on, so the machine chooses. A published image brings a new machine up fast.

Rejected: a crew setting or label (a request does not care how its session runs); a user in the docker group (root-equivalent); OrbStack, Apple's `container` and Docker Desktop on macOS (memory leaks outside the VM's limit, too many open files, licences); the worktree with the main `.git` mounted writable (a way out of the container); `.git` mounted read-only (the session could not commit or branch); a clone with `--reference` and no `--dissociate` (a gc of the host's repository breaks it); the host's full login in every container (every session holds the login); a credential proxy on the host, for now (unproven with subscription logins, the vendors' terms unclear; the preferred route later if they allow it); keys per ship name (a ship may be crewed on any machine) or as a crew option (more moving parts); building from `devcontainer.json` at crew time (slow, and it can fail mid-launch; a later option); a VM per tenant (only when compute is sold).
